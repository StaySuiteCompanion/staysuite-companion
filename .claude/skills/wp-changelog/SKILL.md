# Changelogs that WordPress users can actually use

A WordPress changelog is read by a site owner deciding whether to click "Update now". They do not care about your function names. They care about three things: **will this break my site, will my data survive, and what do I get for it**. Changelogs fail when they are a restated git log.

## Where the changelog lives

| File | Audience | Notes |
|---|---|---|
| `readme.txt` → `== Changelog ==` | wordpress.org plugin page, update screen | The public changelog. Newest entry first. |
| `readme.txt` → `== Upgrade Notice ==` | Update screen only | Shown **only** for security or breaking changes, up to 15 000 characters. |
| `CHANGELOG.d/{version}.md` | The build script | Bullet-only fragment consumed by the release command. |
| GitHub release notes | Contributors and your team | Can be more technical; link the compare view. |

Most plugin repos keep one release flow: notes are drafted as a fragment, the release script inserts them into `readme.txt`. That keeps the version bump and the notes in a single commit, which is what makes a release reproducible.

## Process

1. **Fix the range.** Newest first, exclusive of the previous tag:
   ```bash
   git log --no-merges --pretty=format:'%s' v0.2.0..HEAD
   ```
   `scripts/changelog-collect.sh` does this and groups the result by Conventional Commit type, flagging which commits are normally omitted.
2. **Read the diffs for anything that sounds risky.** A subject line hides a renamed meta key or a dropped hook. `git log --stat` and `git show <sha>` on the ones touching options, post meta, database calls, or anything with "remove", "rename", "migrate" or "default".
3. **Decide the version** from the *content*, not the volume: a data migration or removed hook is major, a new block or setting is minor, a fix is patch. See the `wp-plugin-release` skill for the shipping side.
4. **Write bullets** — user-facing outcome first, in the present tense, one line each, no type labels, no commit hashes, no internal file names.
5. **Write the fragment**, bullets only (the heading is generated by the release script):
   ```markdown
   * Hotel pages: gallery cover and auto-aggregated facilities.
   * Homepage pattern renamed to StaySuite Homepage.
   ```
6. **Add an Upgrade Notice** only when the release can lose data or break a site, placed after `Stable tag` and before `== Description ==` in `readme.txt`:
   ```
   == Upgrade Notice ==

   = 1.0.0 =
   Renames the hotel post type from `vs_hotel` to `ssc_hotel`. A migration runs automatically on upgrade; back up your database first.
   ```
7. **Preview for the update screen.** The Update screen shows the latest three changelog lines, so put the most important outcome first. Owners skim that, not the whole section.

## Writing the bullets

Good:

- `* Hotel pages now show a gallery cover and aggregated facilities.`
- `* Fixed the date strip ignoring the checkout date on mobile Safari.`
- `* Requires PHP 7.4 or newer.` (when the minimum changed)
- `* Adds a Group Requests screen; quotes are emailed to the admin address.`

Bad:

- `* feat(hotel): add GalleryCover component` — internal, no outcome.
- `* Fixed bug in code.` — which behaviour? Users cannot verify it.
- `* Bump to 0.2.0.` — the heading already says that.
- `* Added RoomBadge, HotelCard, PriceFrom, QuickEditBox, FacilityList.` — an inventory, not a description.

House style: sentence case, no trailing period on fragments, past or present tense consistent within a release (present tense reads cleaner for new entries), and lead with the noun the user recognises ("Hotel pages", "Group Requests", "the homepage search") rather than the code that changed it.

## Grouping

Order entries so the reader learns what to do first:

1. **Breaking changes and migrations** - always first, always explicit about what the user must do.
2. **New features** - what they can now do.
3. **Fixes** - what stopped hurting. Include the symptom, not the cause.
4. **Compatibility notes** - minimum WP/PHP versions, deprecated hooks, new filter or action names for developers.
5. **Internal only** - omit `chore`, `ci`, `test`, `docs`, dependency bumps, refactors with no behaviour change. Silence here is not hiding: the git history still has them.

## Longer horizons

When a release accumulates more changes than a screen can hold, do not invent structure the maintainers did not plan - instead:

- split it into several releases (a `0.3.0` block and a `0.2.5` fix rather than one sprawling entry),
- or keep an "Unreleased" section at the top of the fragment directory and promote it at release time.

For a major release with a migration, pair the changelog with an upgrade guide (a `docs/upgrade.md` in the repo, linked from the changelog entry) that describes the old key, the new key, and whether the migration is automatic.

## Common failure modes

- **Forgetting the Stable tag** when adding notes by hand - the entry exists but never reaches the plugin page.
- **Notes for a version that was never tagged**, so the tag and the notes disagree.
- **Documenting a breaking change as a fix.** Under-claiming here costs people data; over-claiming costs you support emails. When unsure, call it breaking.
- **Duplicating the readme description** into the changelog instead of describing the delta.
- **Rewriting history for a released version.** Once a tag exists, that version's notes are frozen; corrections go in the next release.
